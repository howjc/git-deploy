# v0.3 physical target lock audit

Date: 2026-07-14

Scope: every local mutation that can change remote bytes, current state, transaction
journals, deployment history, or target policy. The lock is a single-controller,
cross-process `fcntl.flock`; it is deliberately not a distributed lock.

## Result

PASS after adding the missing lock around `state recover --execute`. Every normal
mutation path now serializes on `<state-base>/targets/<target-id>/target.lock`.
Aliases with an identical physical target payload resolve to the same target ID and
therefore the same lock; distinct physical targets remain independent.

## Mutation entry coverage

| Entry | Lock owner | Coverage |
| --- | --- | --- |
| source/artifact deploy and state-only reconcile | `StateDeploymentExecutor.deploy` / `_state_only` | full transaction, remote mutation, verify, CAS, journal close |
| latest rollback | `StateRollbackService.rollback_latest` | eligibility recheck, remote restore, verify, CAS, journal |
| state bootstrap | `StateBootstrapService.execute` | final remote recheck and generation-1 CAS |
| state recover execute | CLI `_state_recover` | decision recheck, transport restore/finalize, CAS, journal close |
| managed-policy migration | `StatePolicyMigrationService.execute` | open-transaction check, remote read verification, CAS |
| legacy history publish | `StateMigrationService.publish` | each live physical target publish |

Read-only plan, history, verify, doctor and recovery inspection intentionally do not
take the mutation lock. They rely on generation/identity checks and report a
consistent failure if state moves before an authorized mutation.

## Lock ordering and responsibilities

1. Application adapters first use `ApplicationWorker`'s in-process target mutex to
   reject duplicate work in one process.
2. The domain mutation boundary acquires the OS file lock before re-reading mutable
   state and before opening or mutating the remote where the operation requires it.
3. No mutation path acquires a second target lock while holding the first; store and
   transport operations are nested below the one physical-target lock.
4. The worker mutex is responsiveness/idempotency plumbing. `TargetLock` is the
   cross-process correctness boundary; the responsibilities are complementary.

## Crash behavior

The kernel owns the lock through its open file descriptor. Normal exceptions release
it via context/finally; process exit or kill closes the descriptor, so stale PID text
in `target.lock` cannot retain ownership. The file is metadata, not the lock itself,
and must not be manually deleted as a recovery procedure.

Automated evidence: `tests/test_state_lock.py` covers same-target exclusion,
different-target concurrency, cross-process contention and reacquisition after the
holder exits. CLI multi-remote tests cover alias lock sharing and target isolation.
