# ADR 0001：v0.3 收敛为简化稳定 CLI

- 状态：Accepted
- 日期：2026-07-14
- 决策者：项目维护者

## 背景

v0.2.1 已具备 revision 规划、expected state、transaction journal、备份恢复、最新回滚、多 remote、多协议和 artifact build。原 v0.3 计划继续建设 Textual TUI、非最新回滚和引用可达性 GC，但个人长期维护多个项目的主要痛点仍是日常命令参数多、首次配置困难和故障诊断分散。

继续扩张会增加 UI 依赖、交互矩阵、历史谱系算法和删除安全证明的维护成本，却不能优先改善“一条命令可靠上线”的核心场景。

## 决策

v0.3 以 CLI 作为唯一稳定入口，冻结 application service 公共边界，在既有 state/transaction 引擎上实现：可信 current → HEAD 默认计划与部署、默认最新回滚、只读 doctor、可靠性故障注入、真实协议容器演练和最短路径文档。

Textual TUI、Web UI、非最新 deployment 自动回滚和自动 GC 不进入 v0.3.0。历史对象只报告容量，不自动删除。未知远端内容不得自动 adopt。

## 被否决方案

### 继续原 TUI 路线

否决原因：引入 optional UI 依赖、键鼠/尺寸/取消状态测试矩阵和双适配器维护成本，尚无真实使用数据证明收益。

### 同期实现非最新回滚

否决原因：需要路径重叠与谱系派生证明；最新成功 deployment 回滚已覆盖主要事故恢复场景。

### 同期实现引用可达性 GC

否决原因：自动删除错误会破坏回滚和恢复证据。v0.3 先提供容量报告与人工处理建议。

### 自动 adopt 未知远端状态

否决原因：会破坏 Git 与可信 current 作为唯一事实来源的安全模型。

## 后果

正面后果：发布主线更短，日常使用更简单，测试资源集中在锁、事务、恢复和真实协议；基础安装不增加常驻依赖。

负面后果：v0.3 没有图形交互、任意历史回滚和自动空间回收；需要保留高级 `state` 命令处理少数异常，并由使用者人工决定历史清理。

## 重新评估触发条件

只有满足以下任一条件并有可重复数据时才重新评估：

- state/CAS/Git objects 占用超过明确阈值并造成实际磁盘问题，人工保留策略不可接受；
- CLI 的重复操作时间或错误率被真实使用数据证明明显高于可接受水平，且愿意承担 TUI 维护成本；
- 最新回滚无法覆盖高频实际故障，并能证明非最新派生回滚的收益高于复杂性和风险；
- 产品定位明确改变为多人平台，并出现真实 RBAC、审批或审计合规需求。

重新评估必须新建 ADR 和原子任务，不得直接恢复已冻结清单。
