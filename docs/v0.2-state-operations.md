# v0.2 状态、目标与迁移运维

本文说明 named remote、physical target identity、可信 current state 和事务恢复流程。示例中的项目及 remote 名称均为占位名称。

## Named remote 与 physical target

每条命令先选择 remote alias，再为项目计算 physical target。默认 identity 由规范化后的 protocol、host、有效端口、项目名和 `remote_root` 组成；alias、username、密码、私钥、token、build 和 secret 配置不参与计算。

- 两个 alias 指向相同 canonical endpoint/root 时，共享 `target_id`、state 和本地 target lock。
- protocol、host、端口、项目名或 `remote_root` 不同时默认隔离。
- 可配置显式 `target_id`，但同一 ID 不能绑定不同 canonical payload；冲突会在远端连接和 state 访问前被拒绝。
- 多 remote 且没有 `default_remote` 时必须传 `--remote`。可在 TOML 顶层设置 `default_remote = "dev"`，安全地默认到开发环境。

先用只读命令确认选择结果：

```bash
git-deploy plan official --revisions HEAD --remote dev
git-deploy state inspect official --remote dev
```

`plan` 显示 alias 和 `target_id`，但不连接远端或写 state。`state inspect` 只读取本地 generation、identity、policy 和 transaction。

## 从旧目录迁移到 target 布局

v0.2 会发现单 remote 的 `<project-state>/deployments/`，以及旧 named remote 的 `<project-state>/remotes/<alias>/deployments/`。新布局是 `<project-state>/targets/<target-id>/deployments/`。

迁移按 plan、staging、publish 三步进行：

```bash
# 只生成计划
git-deploy state migrate official --remote dev

# 复制到隔离 staging 并验证
git-deploy state migrate official --remote dev --stage

# 重新建立 staging，并在 target lock 下发布
git-deploy state migrate official --remote dev --yes
```

计划会遍历项目的全部 alias。多个 alias 指向同一 target 时合并历史；相同 deployment ID 只有内容一致才可合并。未知 alias 或不兼容历史令计划 `blocked`，不会创建 staging 或发布目录。

staging 位于 `<project-state>/.migration-staging`。staging 失败会清理该目录；publish 中断后可修复原因并重新运行 `--yes`，已发布的同名记录不会被覆盖。发布会写 `migration.json`，不会删除旧目录，因此 legacy 证据始终保留。

## 建立可信 current state

没有 current 时，不从来源未知的远端 bytes 猜测基线。选择可证明的 Git revision，先预览再创建 generation 1：

```bash
git-deploy state bootstrap official --revision COMMIT --remote prod --dry-run
git-deploy state bootstrap official --revision COMMIT --remote prod --yes
```

执行会只读核对远端受管文件与 revision 一致，持久化 Git tree，然后在 target lock 下发布 current；mismatch、identity 变化或并发 generation 都会阻断。

只有确认全部受管 source/artifact destination 应当不存在时才使用 empty：

```bash
git-deploy state bootstrap official --empty --remote dev --dry-run
git-deploy state bootstrap official --empty --remote dev --yes
```

empty 执行仍逐项只读验证远端路径不存在，任一路径存在都会失败。`--dry-run` 或缺少 `--yes` 都只生成计划，不连接远端、不写 current。

若 state 丢失，只能恢复 state 备份，或重新使用已知 revision/已验证 empty bootstrap。v0.2 不会 adopt 未知远端内容为可信 current。

## Identity 与 policy 变化

physical identity mismatch 表示当前配置指向另一目标。先检查配置和 `state inspect`；若目标确实改变，为新目标执行 migration 或 bootstrap，不要复制或手改 current JSON，也不要强行复用旧 `target_id`。

repository identity、include、exclude、protected 或 artifact destinations 改变时，managed policy fingerprint 会变化。先查看计划，再显式执行：

```bash
git-deploy state policy-migrate official --remote prod
git-deploy state policy-migrate official --remote prod --execute --yes
```

execute 在 target lock 下重算完整受管文件表，只读验证新旧路径，再以 CAS 推进一代 state；远端写调用必须为 0。漂移、未完成 transaction 或 generation race 会保留旧 generation。

## 校验、恢复与回滚

```bash
# 本地校验 current、CAS、持久化 Git tree 与 policy
git-deploy state verify official --remote prod

# 增加远端只读核对，仍不写远端
git-deploy state verify official --remote prod --check-remote

# 查看恢复决策；确认后执行可证明安全的动作
git-deploy state recover official --remote prod
git-deploy state recover official --remote prod --execute --yes
```

未知或第三种远端内容会进入 `manual_recovery_required`，不会被猜测覆盖。保留 transaction ID、stage、state 和 backup 证据，修复根因后再次 recover。

v0.2 的 stateful 路径只支持最新成功 deployment 回滚：

```bash
git-deploy rollback official --latest --remote prod --dry-run
git-deploy rollback official --latest --remote prod --yes
```

指定非最新 deployment 会在连接远端前拒绝；历史回滚推迟到 v0.3。`--force` 只允许已确认的远端 hash drift，不能绕过 identity、policy、state integrity、transaction 或 generation 门禁，不应作为日常参数。

v0.2 不删除 state、CAS 或持久化 Git 对象。`git-deploy state gc` 会明确报告不支持；引用可达性 GC 计划在 v0.3 实现。
